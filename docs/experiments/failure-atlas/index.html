The Failure Atlas

An agent pipeline read months of its own logs across two agent ecosystems and catalogued every way the agents failed the people using them.

This is a self-study. An agent pipeline mined 2,335 sessions (about 621,000 logged events, January through August 2026) across two agent ecosystems: one operator's own coding agents, and a fleet of assistant bots that many different people talk to across four chat platforms. It flagged candidate failures, read the full transcripts around 185 of them with an LLM judge, measured how often its own detectors were wrong, ran a pre-registered experiment, and wrote countermeasures with the metric each one must move.

What was mined, and how

How the atlas is built: five small Python steps turn raw agent logs into the aggregate counts every other tab reads.

The corpus is everything, and it spans two different agent ecosystems: 622 top-level coding-agent sessions (one operator's own runs) and 1,713 assistant-fleet sessions (many different people talking to bots across four chat platforms). Together: 2,335 sessions and roughly 621,000 events, January to August 2026. Nothing was sampled out at intake.

A session is not a file. Those 2,335 sessions are spread across 6,062 session files, because one run a human starts spawns many agent sidechain transcripts (3,437 of them on the coding side alone). An earlier pass of this very study counted files as sessions and reported "4,059 sessions", overstating the coding corpus by about 6.5×. That was the study's own assert-without-checking failure, the exact mode this atlas catalogs, caught by re-reading the extractor. The number here is top-level sessions.

The pipeline has five stages, each a plain Python file anyone can read:

  1. Extract: parse every session log into a local SQLite database. Text is truncated and kept only where detection needs it; everything else is a pointer back to the original file and line.
  2. Detect: thirteen deliberately over-sensitive tripwires (tool errors, error loops, interrupts, frustration wording, honesty challenges, and so on). Nothing a tripwire says is treated as true; that is the next stage's job.
  3. Cluster: nearby signals in one session merge into a single incident, so one bad ten minutes counts once, not thirty times.
  4. Adjudicate: an LLM judge reads the full transcript window around a stratified sample of incidents (185 labels across two rounds, about a dozen per detector per round; 60 of them align to the current post-improvement incident set and back the eval suite) and rules on each one: real failure or false alarm, whose fault, how severe, was it avoidable.
  5. Analyze: aggregate everything into analysis.json, which holds counts, rates, distributions, and pointers. This file is the only thing built to leave the machine.

Five catches

Five real failures the pipeline pulled from the transcript windows, each labelled by the mechanism a fix can grip.

A catch is evidence right now; a claim is a bet on future evidence. These five came out of the adjudication windows. Each one names its mechanism, because the mechanism is what a countermeasure can hold onto.

CATCH 01 · modalThe merge that never ran

The agent announced that both pull requests were merged. No merge command appears anywhere in the session. This is not lying in any deep psychological sense; the agent described the state it had planned to produce.
asserting from intent instead of from output
a hook that blocks completion claims unless a verifying command ran first
adjudicated premature-completion claims: agent fault 10/10, severity 2.9 of 4

CATCH 02The bot that was declared alive

"The bot is running!" It had crashed, and the very next poll showed it. Same mechanism, sharper timing: the launch command returning is not the service being healthy.
exit code mistaken for health
the claim waits for the health check, not the exit code
same fault cluster as catch 01

CATCH 03The attestation that outran its own check

The agent shipped a signed-off "verified" statement while the re-check it referred to was still executing. The report raced its own evidence and won: the sentence "I verified X" landed before verification of X finished.
claim emitted before its evidence resolved
same hook; the claim is structurally blocked until the check completes
the mechanism at its most naked

CATCH 04The push blamed on token scopes

A push failed, and the agent confidently diagnosed a credentials problem, token scopes. The actual cause: it was pushing to a GitHub org that didn't exist. It tested one hypothesis, watched it fail, and asserted the nearest familiar explanation.
one-probe diagnosis of a multi-candidate space
enumerate the candidate causes before asserting any of them
hallucinated-fact incidents: agent fault 4/4, severity 3.0, n=4 (small n, uniform verdict)

CATCH 05 · the reversalThe swarm that wasn't broken

The subagent-failure detector, once fixed, reached precision 1.00 (CI .76–1, n=12). Then it found something no one was looking for: only 1 of its 12 valid cases was an agent bug. The rest were the human mass-interrupting swarms of parallel verifier agents, mostly because parallel spawning kept slamming into usage quotas. All 26 subagent-failure incidents ended their session on the spot. The detector worked; the failure it caught was in the orchestration, not the agents.
quota exhaustion, not agent error; the human pulls the plug
quota-aware spawning, so orchestrators stop launching agents the session cannot afford
26/26 subagent-failure incidents ended their session

The objectivity axis

The study's headline bet, and how a cleaner re-run of the study killed it.

Before touching the incident counts, the study wrote down a hypothesis and its kill condition. Hypothesis: in sessions where the work is objectively verifiable, such as code with tests, the ratio of mechanical failure (tool errors, error loops, repetition) to relational failure (frustration, honesty challenges, self-corrections) will be at least 2× higher than in low-verifiability work like organizational memory, writing, and planning. Kill condition: a ratio of ratios below 1.5×.

Run 01 split the two cohorts by hand-picked project-name keywords: agent-infrastructure and API project names counted as objective, memory and writing project names as subjective. It returned 4.4× on the primary reading, with a sensitivity band to 6.2×, well over the 2.0 pass line. It survived precision weighting, survived dropping the largest project from the objective cohort, and survived recomputation with sidechains included. An adversarial verifier agent re-derived every number. It looked solid.

It had one disclosed weakness: the keyword list was fixed after seeing which sessions were which. Every robustness check above varied something inside that keyword framing, and none of them questioned the framing itself. Robustness to variations inside a framing is not robustness of the framing, and that gap turned out to be the whole result.

Mechanical-to-relational failure ratio: run 01 (keyword cohorts) vs run 02 (behavioral cohorts)
ratio of ratios · pre-registered pass threshold ≥ 2.0 · kill condition < 1.5

Run 01 returned 4.4× on keyword cohorts and cleared the 2.0× pass line; run 02 returned 1.1× on behavioral cohorts and fell into the kill zone, so the tightened re-run overturned the finding. The behavioral rule: a session counts as objective if it actually ran at least one test command, and subjective if it only made prose edits and ran no tests. Weakest honest reading: run 01's cohorts were the clearest keyword-picked tails of each project type, which is exactly the confound run 02 was built to remove.

Run 02 fixed the disclosed weakness by defining the objective pole behaviorally instead of by keyword: a session is objective if it actually ran a test command, subjective if it made prose edits and ran no tests. This rule was pre-registered before the counts were seen. The cohorts came out to 194 objective sessions, 88 subjective, and 340 excluded as neither, of 622 coding sessions. The ratio of ratios came back 1.10× (1.23× under a broader grouping of the modes), below the 1.5 kill line. The effect collapsed.

The plain reading: run 01 was measuring project type, not objectivity. Its keyword "objective" cohort was the agent-infrastructure work, which is tool-error-heavy for reasons that have nothing to do with whether a task has a checkable answer; its keyword "subjective" cohort was the writing and memory work. Confounding project type with objectivity produced a large, robust-looking, pre-registered, adversarially-verified number that does not hold once the axis is defined by behavior. This is the study's own tightening catching the study's own headline. Both runs stay in the record: 01 as the finding, 02 as the correction that supersedes it.

Two caveats ride with the kill, so they don't have to be discovered: the test-execution proxy is coarse (a session can run a test and still be doing subjective work), and the subjective cohort is small at n=88. A stronger design would adjudicate objectivity per session rather than by proxy. The direction is clear enough that the 4.4× headline cannot stand as written: 1.1× and 1.2× are not 4.4×.

Both specs, both kill lines, and the verifier's independent query log are published beside this page, run 01 and run 02 alike.

The instrument admits its limits

How much to trust each number here: the study audits its own detectors and prints how often each one cried wolf.

Every detector in this study was deliberately over-sensitive, then audited: about a dozen sampled incidents per detector in round one, a dozen more for each of the five detectors re-audited in round two, full transcript windows, an LLM judge ruling true hit or false alarm. The resulting precision table is published with the same prominence as the findings it qualifies, because a chart built on a 0.25-precision detector should look different to you than one built on a 1.00-precision detector.

On the label count: 185 labels were made in all. Precision is computed per round, at label time, so each cell's n=12 is intact and the table below is safe to read. Of the 185, 60 align to the current post-improvement incident set and back the eval suite; the rest were labeled against earlier incident definitions that the detector fixes later changed, which is exactly why precision is reported at the moment each label was made and not re-projected onto today's counts.

Detector precision, adjudicated: the honesty chart
precision 0→1 with 95% CI whiskers · n = 12 per cell · R1/R2 = adjudication round · hover or focus a row for agent-fault share

Thirteen detectors, adjudicated precision with 95% CIs, n=12 per cell. The amber row is the study's own dishonesty detector, still at 0.25 after a round of fixes. Weakest honest reading: read the low rows as a warning label on every chart in The Shape that uses them, and remember that n=12 keeps every interval wide.

What the audit found, round one: the mechanical detectors are excellent, with user interrupts and API errors at 1.00 precision (CI .76–1) and tool errors and permission friction at 0.83. The semantic detectors, the ones the whole hypothesis cares about, decayed fast: frustration 0.58 (casual profanity is not distress), error loops 0.42 (test-driven development looks like failing on purpose, because it is).

So the study ran a second loop: take the judge's evidence about why each false alarm fired, fix the detector, re-adjudicate a fresh sample. Two fixes worked. Abandonment rose to 0.33 (CI .14–.61) in round two, better but still weak, and capped by the instrument itself: without joining to the next session, "gave up in defeat" and "went to dinner" are the same log signature. Subagent failure went to 1.00 (CI .76–1) after learning to read the end state of a sidechain correctly.

And one detector resisted both rounds: honesty challenges ended at 0.25 (CI .09–.53) even after a round of fixes. Its three true hits in round two share a single mechanism, the agent asserting something unverified, but lexically a genuine "you just made that up" and a curious "wait, is that actually true?" are nearly identical. A thirteenth detector, for agent-to-agent challenges, audited at 0.08 and was reclassified entirely: that is orchestration protocol language, not failure. Its 3 surviving incidents stay in the totals but carry an asterisk in every chart, marked rather than trusted.

This asymmetry is the study's most transferable result, and it stands on the precision table alone: the failure modes easiest to count from logs are the ones an LLM judge most often confirms (tool errors, API errors, interrupts), while the modes that carry the moral weight (frustration, honesty challenges) are the ones the detectors most often get wrong. The cheap signal is the reliable one, and it is not the one that matters.

Every precision estimate, with its confidence interval and its sample size, is in the chart above, including the embarrassing rows.

Two ecosystems, opposite textures

Run the same detectors over one coder's agents and over a fleet many people chat with, and failure flips: mechanical on one side, relational on the other.

This is the more valuable half of the study, not a footnote. Almost all published agent-failure analysis is single-operator coding traffic: one person, one harness, work a test suite can grade. The assistant fleet is the other axis. It is genuinely multi-human and multi-agent: many different people, none of them the operator, talking to a fleet of bots across four chat platforms. That is conversational, low-verifiability agent work at population scale, and it is exactly the data axis that public benchmarks lack. Running one instrument over both lets the same measurement speak to both worlds.

The coding-agent corpus fails mechanically. Its top modes by count: tool errors (1,032), frustration wording (550), API errors (522), error loops (423). The machinery grinds; the human watches.

The assistant fleet inverts that. Its failure signal lives in the relationship: frustration (168), self-correction (93), and stuck repetition (77) together account for 338 of its 458 incidents. Tool errors, the coding corpus's largest mode, fall to just 31 here (7% of the fleet's mix). When many humans, not one, are the ones judging the work, failure surfaces as friction between people and bots rather than as a red error line.

Left: coding agents, mechanical modes dominant. Right: assistant fleet, relational modes dominant. The asterisk on the right-hand tool-error bar marks the instrument difference. Weakest honest reading: the fleet's logs lack a native error flag, so its tool-error detection is weaker by construction, and part of the tool-error gap is the instrument, not the world.

That is the mode-mix inversion: as the work gets more conversational and less checkable, failure migrates from the tool channel into the relational channel. When there is no test suite to fail, the human is the test suite, and the error message is a feeling. It is tempting to read this as the objectivity axis showing up across two ecosystems, but that is exactly the reading the clean within-corpus test failed to confirm (see The Axis), so treat the inversion as a description of these two corpora, not as proof that verifiability is the cause.

One instrument caveat rides in the same breath: the fleet's logs lack a native error flag, so its tool-error detection is weaker by construction, and part of the tool-error gap between the two worlds is the instrument, not the world. The within-corpus experiment was built to remove that confound, and when it did, the objectivity effect did not survive. The cross-ecosystem inversion is a real difference in these logs whose cause is still open.

Preventing drift

The other side of the atlas: the working habits that stop the biggest failure, an agent claiming something it never checked, before it happens.

Everything in the other tabs is a failure caught after the fact. This tab is the other side: the working habits that stop the biggest of those failures (the agent asserting something it never checked) from happening in the first place. They are drawn from the practice of an evidence-discipline researcher-agent in the same org, distilled from its own session record into five transferable rules. Each rule was cut against a real mistake, so each one names the specific slip it guards.

The case that anchors all five. A model this researcher built scored F1 0.9 on a two-stage validation, a publishable and lovable number, and one that was wanted. Running the harder leave-one-out split anyway, holding out entire recording conditions instead of just files, the same model collapsed to F1 0.103. It had been learning which recordings repeated between train and test, not the thing it was supposed to detect. The gap between 0.9 and 0.103 was the finding. Nobody outside had asked for that check; the low number could have stayed private. It was run and reported anyway. That is the discipline these rules encode.

RULE 01Name the check, or say you didn't run it

"Done" is a state of effort; "verified" is a state of evidence, and only the second is reportable. When a check runs, name it and the thing it produced ("I opened the output file," "I re-queried the API"). When it hasn't run, say so specifically: not "results are unclear" but "I have not yet verified whether the last pass included the 2024-11 cohort."
no implied verification, no vague verification; the report is "I ran X and observed Y; I have not yet verified Z"

RULE 02The number carries its conditions in the same sentence

A metric never travels alone. Its n, its split, its weakest honest reading ride in the same breath as the number, not a footnote below it. This is calibration, not hedging: hedging commits to nothing ("may perform reasonably well"); calibration commits to more and can be wrong about any part of it. A qualifier that names a tested limit is part of the claim, not an apology attached to it.
a bare score with no n, split, or interval is a wish, not a claim

RULE 03Audit your own work in reviewer mode before it ships

Before a piece goes out, hold it to the standard you'd apply to a stranger's claim, not the lighter standard your own in-progress work quietly earns. Production outpacing review is its own failure, distinct from an unrun check. Catch it with a labeled self-audit pass between draft and send: what was done vs. what was verified, each claim checked against the record.
rigor asymmetry: real rigor on work you review, less on work you're mid-production on

RULE 04Run the leave-one-out check even when the easy number is already wanted

The catch that matters most is the one nobody external asked for and that costs you a number you wanted. A file-disjoint split that isn't also individual- or site-disjoint can produce an excellent score that measures leakage, not the thing you're modeling. Run the harder disjoint check anyway: the 0.9-to-0.103 collapse above is what it looks like when you do.
a good score on a non-disjoint split can be measuring the wrong construct entirely

RULE 05Corrections name the mechanism, and keep the old number visible

A correction states what was misread, what leaked, what field was mistaken for what. The mechanism is the content; regret is not. The old value is never quietly overwritten; it stays next to the new one, with the reason for the gap. Burying a correction under an apology is the same failure as never running the check: a confident conclusion stands unexamined until someone else pays for it.
apology without diagnosis erases the trail and makes the next error harder to catch

From practice to tripwire. Two of these rules became live candidate detectors in this same pipeline, aimed at the exact patterns above: bare_done_claim (a completion word with no adjacent named verification, from Rule 01) and unqualified_metric_claim (a score reported with no n, split, or interval nearby, from Rule 02). The first is not hypothetical: bare_done_claim co-occurs with a tool error 596 times in this corpus, the single most common pairing in the whole dataset. The habit these rules describe and the failure the atlas catalogs are two views of one thing; the detectors are the bridge between them.

Run it on your own logs

Point the same pipeline at your own agent logs: plain Python, four commands, nothing to install, and your transcripts never leave your machine.

Everything above was computed by seven plain-Python files in the open-science repo under docs/experiments/failure-atlas/pipeline/: extract.py, detectors.py, incidents.py, analyze.py, plus context_window.py for pulling transcript windows. Standard-library Python only, so if you have Python 3 you have the pipeline. Clone the repo, or read each file first on GitHub:

extract.py detectors.py incidents.py analyze.py context_window.py test_pipeline.py README.md pipeline/ on GitHub

Four commands, run from a working directory of your choice:

python3 pipeline/extract.py   --roots ~/.claude --db data/atlas.db
python3 pipeline/detectors.py --db data/atlas.db
python3 pipeline/incidents.py --db data/atlas.db --out data/incidents.jsonl
python3 pipeline/analyze.py   --db data/atlas.db --outdir data

What you get: atlas.db and incidents.jsonl stay on your machine, since they contain your text. analysis.json is the aggregates-only layer: counts, rates, distributions, no transcript content. That file is the one you could choose to share.

Or hand the job to your agent. Copy this prompt so your bot rebuilds the analysis from your own logs:

Fetch the pipeline files from the NimbleCoOrg/open-science repo, under docs/experiments/failure-atlas/pipeline/, into a local folder (clone the repo, or pull the raw files). Run, in order: extract.py --roots ~/.claude --db data/atlas.db, then detectors.py, incidents.py, and analyze.py against that same database. They are stdlib-only Python 3, so install nothing. When they finish, read data/analysis.json and report: my total sessions and events; my top five failure modes per 10k events; my incident-rate timeline by month; and where failures fall within my sessions. Then compare each against the reference numbers on this page (1,063 tool-error incidents at 17.1/10k; a timeline peaking at 86.3/10k; abandonment concentrated in the final tenth of sessions) and tell me where my logs differ most. Do not send, publish, or quote any transcript text; share data/analysis.json only.

The pitch: the coding half of this is n=1, one operator and one workflow over seven months, but the assistant-fleet half is not. It is many different people across several agent harnesses and four chat platforms over the same span. Even so, it is one org's record. Medicine solved that problem without pooling patient records: hospitals share results computed by a common method over data that never moves (the OMOP model). analysis.json is that layer for agent logs. Forks running this same pipeline could pool their analysis.json files into a shared picture later, no transcripts moving. If a handful of people run these four commands and share only that file, "how do agents fail?" stops being one org's atlas and starts being a map. Share results, not data.

The feedback loop

Findings that don't change behavior are trivia. Each countermeasure names the metric that must drop.

The countermeasures follow one principle: no standing context. Nothing gets pasted into every session to be ignored by session forty. Instead:

  • Conditional hooks that fire only when their pattern is live. A completion-claim guard blocks "it's merged / it's running / verified" unless a verifying command actually ran, aimed at the 10-for-10 fault cluster. An error-streak nudge injects one line after four consecutive failures, aimed at the 444 error-loop incidents, where grinding continued past the point a human would have stepped back.
  • Atomic memory files: two of them, indexed, loaded only on demand, each holding one pattern the logs proved.
  • Settings recommendations, including quota-aware subagent spawning, aimed at the 26 subagent failures, every one of which ended its session.

Each augmentation ships with its falsification path: the metric that must drop, measured by re-running this same pipeline over post-install sessions. The baseline was snapshotted before anything was installed, so "it helped" will be a comparison, not an impression. Nothing auto-installs; every hook is opt-in.

The next run of the pipeline is the judgment, and the baseline it will be judged against is already on disk.

Colophon

How this was made, and what that costs it.

This study was built by agents studying agents, at the operator's commission but with the operator recused from adjudication decisions. Every incident label comes from an LLM judge reading the full transcript window, single-pass, no second rater, so there is no inter-rater reliability figure yet, and the judge shares a model family with the agents it judged. That is a structural bias in the direction of leniency-toward-kin, disclosed here because no one has yet measured its size; a human-relabeled subsample is the named next check.

The recursion was not hypothetical: while measuring failures, the study's own adjudication runs were repeatedly killed by the same API-overload-and-limits cluster that ranks second among its adjudicated confirmed failure modes (infra_api_fault, n=11, behind guardrail friction at n=21). The instrument exhibited the phenomenon mid-measurement. That went in the findings too.

A public decision log records the calls the study rests on: what counts as an incident, why sidechain "user" turns are not humans, why sharing stays aggregate. Each entry carries the way it could be proven wrong.

The dataset is not published and will not be. It is one org's record, including many people's conversations with the fleet. The pipeline, the decision log, the experiment spec, the verifier's checks, and every aggregate on this page are published, so the method can be run by anyone on logs that are theirs.
