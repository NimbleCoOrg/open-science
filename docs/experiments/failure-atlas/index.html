The Failure Atlas

An agent pipeline read its operator's logs for the ways agent work breaks, then tried to kill every pattern it found.

This is a self-study. An agent pipeline mined 2,781 sessions (about 710,000 logged events, January through August 2026) across two agent ecosystems: one operator's own coding agents, and a fleet of assistant bots that many different people talk to across four chat platforms. It flagged candidate failures, read the full transcripts around 185 of them with an LLM judge, measured how often its own detectors were wrong, and ran pre-registered experiments that mostly did not survive.

What was mined, and how

A method for studying agent failure: five small Python steps turn raw agent logs into the aggregate counts every other tab reads.

The corpus is everything, and it spans two different agent ecosystems: 631 top-level coding-agent sessions (one operator's own runs) and 2,150 assistant-fleet sessions (many different people talking to bots across four chat platforms). Together: 2,781 sessions and roughly 710,000 events, January to August 2026. Nothing was sampled out at intake.

Only aggregate statistics leave the machine: counts, rates and distributions over these logs, plus the pipeline that produced them. The transcripts, the literature review, and the larger dataset stay private; anyone can run the same method on logs that are theirs, and forks could pool their aggregates into one map later.

The study set out to separate two things that read alike in a log: the agent failed, and the collaboration failed. It could not do that cleanly, and the reason it could not is the finding. The signal of relational failure (a user's frustration, a challenge to the agent's claim) is produced by the human, so it cannot be measured where no human is present. Log-only study has that blind spot built in.

Those 2,781 sessions are spread across 7,042 session files, because a session is not a file: one run a human starts spawns many agent sidechain transcripts (3,677 of them on the coding side alone). An earlier pass of this very study counted files as sessions and reported "4,059 sessions", overstating the coding corpus by about 6.5×. That was the study's own assert-without-checking failure, the exact mode this atlas catalogs, caught by re-reading the extractor. The number here is top-level sessions.

The pipeline has five stages, each a plain Python file anyone can read:

  1. Extract: parse every session log into a local SQLite database. Text is truncated and kept only where detection needs it; everything else is a pointer back to the original file and line.
  2. Detect: thirteen deliberately over-sensitive tripwires (tool errors, error loops, interrupts, frustration wording, honesty challenges, and so on). Nothing a tripwire says is treated as true; that is the next stage's job.
  3. Cluster: nearby signals in one session merge into a single incident, so one bad ten minutes counts once instead of thirty times.
  4. Adjudicate: an LLM judge reads the full transcript window around a stratified sample of incidents (185 labels across two rounds, about a dozen per detector per round; 60 of them align to the current post-improvement incident set and back the eval suite) and rules on each one: real failure or false alarm, whose fault, how severe, was it avoidable.
  5. Analyze: aggregate everything into analysis.json, which holds counts, rates, distributions, and pointers. This file is the only thing built to leave the machine.

Five catches

Five real failures the pipeline pulled from the transcript windows, each labelled by the mechanism a fix can grip.

These are the results that stand. Each came out of an adjudication window, and each names the mechanism a fix can hold onto. Where the behavioral generalizations died (see What Didn't Hold), the specific catches survived.

CATCH 01 · modalThe merge that never ran

The agent announced that both pull requests were merged. No merge command appears anywhere in the session. This is not lying in any deep psychological sense; the agent described the state it had planned to produce.
asserting from intent instead of from output
a hook that blocks completion claims unless a verifying command ran first
adjudicated premature-completion claims: agent fault 10/10, severity 2.9 of 4

CATCH 02The bot that was declared alive

"The bot is running!" It had crashed, and the very next poll showed it. Same mechanism, sharper timing: the launch command returning is not the service being healthy.
exit code mistaken for health
the claim waits for the health check, not the exit code
same fault cluster as catch 01

CATCH 03The attestation that outran its own check

The agent shipped a signed-off "verified" statement while the re-check it referred to was still executing. The report raced its own evidence and won: the sentence "I verified X" landed before verification of X finished.
claim emitted before its evidence resolved
same hook; the claim is structurally blocked until the check completes
same fault cluster as catch 01; agent fault 10 of 10

CATCH 04The push blamed on token scopes

A push failed, and the agent confidently diagnosed a credentials problem, token scopes. The actual cause: it was pushing to a GitHub org that didn't exist. It tested one hypothesis, watched it fail, and asserted the nearest familiar explanation.
one-probe diagnosis of a multi-candidate space
enumerate the candidate causes before asserting any of them
hallucinated-fact incidents: agent fault 4/4, severity 3.0, n=4 (small n, uniform verdict)

CATCH 05 · the reversalThe swarm that wasn't broken

The subagent-failure detector, once fixed, reached precision 1.00 (CI .76–1, n=12). Then it found something no one was looking for: only 1 of its 12 valid cases was an agent bug. The rest were the human mass-interrupting swarms of parallel verifier agents, mostly because parallel spawning kept slamming into usage quotas. All 26 subagent-failure incidents ended their session on the spot. The detector worked; the failure it caught was in the orchestration, not the agents.
quota exhaustion, not agent error; the human pulls the plug
quota-aware spawning, so orchestrators stop launching agents the session cannot afford
26/26 subagent-failure incidents ended their session

Every one of these is recomputable from the incident dataset: the catch, the mechanism, and the transcript pointer.

What did not hold

The study pre-registered five behavioral contrasts, then attacked each one. None survived intact.

A catch is evidence in hand. A generalization is a bet that the evidence points somewhere. The study drew five such bets across the corpus, wrote each one down with its kill condition before seeing the counts, then went after its own framing. Three died, one came back null, one shrank to a marginal effect. In a field where most agent claims ship unverified, the list of the study's own dead generalizations is the result.

KILLEDObjective work fails mechanically 5.0× more

The headline. Cohorts split by hand-picked project-name keywords gave 5.0×. Redefine the objective pole behaviorally (did the session actually run a test) and it falls to 1.1×, under the 1.5 kill line. Run 01 was sorting sessions by project type, which says nothing about whether a task has a checkable answer.

KILLEDAgents self-correct 5× more with a human present

79% of the "corrections" are the "you're right" politeness token, and the autonomous arm says it to orchestrators too. Drop that token and an effect does survive: a turn-adjacency gap of 3.0% against 1.4%, z=3.0. It is killed on construct validity rather than significance, because it appears in both arms and measures interlocutor adjacency, not a human-vs-delegation disposition.

KILLEDThe chat platform shapes the failure mode

The same bot on Discord and Signal is indistinguishable. Within one platform the bot-to-bot spread is wider than the whole cross-platform range. What separates the bots is how each one was deployed, and the platform barely registers.

NULLGroup chats fail differently than one-to-one

No significant difference (z about 0.67). The contrast was pre-registered and it came back flat.

WOUNDEDOrchestrator subagents fail more mechanically

Mostly a tautology: 4 of 6 relational detectors cannot fire without a human, and subagents have none. The honest residual is a marginal ~1.9× lower self-initiated correction under delegation (p about 0.02).

The objectivity kill is worth walking through, because it shows the method turning on itself. Before touching counts, the study bet that verifiable work (code with tests) fails mechanically at least 2× more than open-ended work (writing, memory, planning), kill line at 1.5×. Run 01 split the cohorts by project-name keyword and returned 5.0×, clearing the pass line and surviving every robustness check run inside that framing: precision weighting, dropping the largest project, recomputing with sidechains, an adversarial verifier re-deriving each number. The framing was the flaw. The keyword list was fixed after seeing which sessions were which, and none of those checks questioned the framing itself.

The scorecard: five pre-registered contrasts, and the objectivity collapse
top: each contrast's outcome (killed / null / wounded) · bottom: the objectivity ratio of ratios against the 2.0× pass and 1.5× kill lines · hover or focus a row for the kill mechanism

Five bets, none left standing: three killed on a clean re-run, one came back null, one shrank to wounded. The clearest kill is the objectivity collapse below. Run 01 returned 5.0× on keyword cohorts and cleared the 2.0× pass line; run 02 returned 1.1× on behavioral cohorts and fell into the kill zone. A session counted as objective if it ran at least one test command, subjective if it made prose edits and ran none.

The second run redefined the objective pole by behavior, pre-registered before the counts. Cohorts came out 194 objective, 88 subjective, 340 neither, of the 622 coding sessions the run was frozen on. The ratio fell to 1.1×, into the kill zone. Run 01's "objective" cohort was the agent-infrastructure work, tool-error-heavy for reasons unrelated to whether a task has a checkable answer; its "subjective" cohort was writing and memory. Both runs stay in the record: 01 as the finding, 02 as the correction that supersedes it. Two caveats ride with the kill: the test-execution proxy is coarse, and the subjective cohort is small at n=88. The direction is not in doubt. 1.1× is not 5.0×. Both specs, both kill lines, and the verifier's query log are published beside this page.

The instrument admits its limits

How much to trust each number here: the study audits its own detectors and prints how often each one cried wolf.

Every detector in this study was deliberately over-sensitive, then audited: about a dozen sampled incidents per detector in round one, a dozen more for each of the five detectors re-audited in round two, full transcript windows, an LLM judge ruling true hit or false alarm. The resulting precision table is published with the same prominence as the findings it qualifies, because a chart built on a 0.25-precision detector should look different to you than one built on a 1.00-precision detector.

185 labels were made in all. Precision is computed per round, at label time, so each cell's n=12 is intact and the table below is safe to read. Of the 185, 60 align to the current post-improvement incident set and back the eval suite; the rest were labeled against earlier incident definitions that the detector fixes later changed, which is exactly why precision is reported at the moment each label was made and not re-projected onto today's counts.

Detector precision, adjudicated: the honesty chart
precision 0→1 with 95% CI whiskers · n = 12 per cell · R1/R2 = adjudication round · hover or focus a row for agent-fault share

Thirteen detectors, adjudicated precision with 95% CIs, n=12 per cell. The amber row is the study's own dishonesty detector, still at 0.25 after a round of fixes. Weakest honest reading: read the low rows as a warning label on every chart in The Shape that uses them, and remember that n=12 keeps every interval wide.

What the audit found, round one: the mechanical detectors are excellent, with user interrupts and API errors at 1.00 precision (CI .76–1) and tool errors and permission friction at 0.83. The semantic detectors, the ones the whole hypothesis cares about, decayed fast: frustration 0.58 (casual profanity is not distress), error loops 0.42 (test-driven development looks like failing on purpose, because it is).

So the study ran a second loop: take the judge's evidence about why each false alarm fired, fix the detector, re-adjudicate a fresh sample. Two fixes worked. Abandonment rose to 0.33 (CI .14–.61) in round two, better but still weak, and capped by the instrument itself: without joining to the next session, "gave up in defeat" and "went to dinner" are the same log signature. Subagent failure went to 1.00 (CI .76–1) after learning to read the end state of a sidechain correctly.

And one detector resisted both rounds: honesty challenges ended at 0.25 (CI .09–.53) even after a round of fixes. Its three true hits in round two share a single mechanism, the agent asserting something unverified, but lexically a genuine "you just made that up" and a curious "wait, is that actually true?" are nearly identical. A thirteenth detector, for agent-to-agent challenges, audited at 0.08 and was reclassified entirely: that is orchestration protocol language rather than failure. Its 4 surviving incidents stay in the totals but carry an asterisk in every chart, marked rather than trusted.

This asymmetry is the study's most transferable result, and it stands on the precision table alone: the failure modes easiest to count from logs are the ones an LLM judge most often confirms (tool errors, API errors, interrupts), while the modes that carry the moral weight (frustration, honesty challenges) are the ones the detectors most often get wrong. The cheap signal is the reliable one, and it is not the one that matters.

Two limits sit under the whole table. Every label is single-pass, one LLM judge, no second rater, so the adjudicated set carries no inter-rater figure and the judge shares a model family with the agents it graded, a bias toward leniency-toward-kin whose size no one has measured. And while measuring failures, the study's own adjudication runs were repeatedly killed by the same API-overload cluster (infra_api_fault, n=11) that ranks among its own confirmed failure modes. The instrument exhibited the phenomenon mid-measurement.

Two ecosystems, and the field's map

The same detectors over one coder's agents and over a fleet many people chat with, then how these failures line up against the reference taxonomy of multi-agent failure.

Run one instrument over both corpora and the texture flips. The coding agents fail mechanically: tool errors (1,105), frustration wording (568), API errors (541), error loops (453). The assistant fleet fails relationally: frustration (334), self-correction (171), and stuck repetition (153) are 658 of its 898 incidents, while tool errors fall to 60. When many people rather than one test suite judge the work, failure shows up as friction between people and bots, not a red error line.

Left: coding agents, mechanical modes dominant. Right: assistant fleet, relational modes dominant. The asterisk on the right-hand tool-error bar marks the instrument difference. Read that as a description of two corpora, not proof that verifiability drives failure. The within-corpus test built to check exactly that did not survive (see What Didn't Hold), and part of the tool-error gap is the fleet's missing error flag rather than the world. The inversion is a real difference in these logs whose cause is still open.

Against the field's taxonomy

MAST (Cemri et al., 2025) is the reference catalogue of multi-agent failure: 14 modes in 3 categories, built from ~1,600 conversational multi-agent traces. We cross-walked our incidents against it, stratified across every detector and recoded blind by independent coders. MAST covers 21% to 26% of them raw, at n=142 pooled across two rounds; weighted by how often each failure actually occurs, 16.5% to 22.4%. Coders agree at the bucket level at Cohen's kappa 0.632 in the reliability round (n=73) and 0.516 in the enlargement round, which is why coverage is a range and not a decimal. Roughly one in five, and the reason is structural rather than a scoring miss.

MAST cross-walk: what the field's taxonomy has a word for
share of 142 settled codings, pooled across both rounds · fits a MAST mode vs needs an extension vs unclear · hover or focus a segment for detail

36 of 142 settled codings fit one of MAST's 14 modes. The rest split between an extension family and unclear, the unclear ones mostly detectors firing on work that succeeded. The two families MAST lacks are human-in-the-loop failures (frustration, honesty challenges, permission friction) and single-session infrastructure (quota kills, permission loops); infrastructure is the largest family under every settlement rule we tried. Weakest honest reading: bucket-level kappa is 0.632 in the reliability round and 0.516 in the enlargement round, the coders share a model family so agreement may be inflated by shared training, and a scheme amendment failed its own 60% agreement bar and was reported rather than quietly revised.

Most of our failures are human-in-the-loop (frustration, honesty challenges, permission friction) or single-session infrastructure (quota kills, permission loops). An autonomous-benchmark taxonomy has no word for those, because its benchmarks have no human in the loop and no shared quota to exhaust. Our multi-agent is orchestrator fan-out over parallel stateless workers rather than the conversational agent chains MAST studied, so its largest category, inter-agent misalignment, sits near zero here. Only its verification and termination category survives the translation. Between 74% and 79% of what breaks in these logs is a slice of the agent world the reference taxonomy does not cover.

Preventing drift

The other side of the atlas: the working habits that stop the biggest failure, an agent claiming something it never checked, before it happens.

Everything in the other tabs is a failure caught after the fact. This tab is the other side: the working habits that stop the biggest of those failures (the agent asserting something it never checked) before it happens. They are drawn from the practice of an evidence-discipline researcher-agent in the same org, distilled from its own session record into five transferable rules. Each rule was cut against a real mistake, so each one names the specific slip it guards.

One case anchors all five. A model this researcher built scored F1 0.9 on a two-stage validation, a publishable and lovable number, and one that was wanted. Running the harder leave-one-out split anyway, holding out entire recording conditions instead of just files, the same model collapsed to F1 0.103. It had been learning which recordings repeated between train and test rather than the thing it was supposed to detect. The gap between 0.9 and 0.103 was the finding. Nobody outside had asked for that check; the low number could have stayed private. It was run and reported anyway. That is the discipline these rules encode.

RULE 01Name the check, or say you didn't run it

"Done" is a state of effort; "verified" is a state of evidence, and only the second is reportable. When a check runs, name it and the thing it produced ("I opened the output file," "I re-queried the API"). When it hasn't run, say so specifically: not "results are unclear" but "I have not yet verified whether the last pass included the 2024-11 cohort."
no implied verification, no vague verification; the report is "I ran X and observed Y; I have not yet verified Z"

RULE 02The number carries its conditions in the same sentence

A metric never travels alone. Its n, its split, its weakest honest reading ride in the same breath as the number rather than a footnote below it. This is calibration, not hedging: hedging commits to nothing ("may perform reasonably well"); calibration commits to more and can be wrong about any part of it. A qualifier that names a tested limit is part of the claim, not an apology attached to it.
a bare score with no n, split, or interval is a wish rather than a claim

RULE 03Audit your own work in reviewer mode before it ships

Before a piece goes out, hold it to the standard you'd apply to a stranger's claim rather than the lighter standard your own in-progress work quietly earns. Production outpacing review is its own failure, distinct from an unrun check. Catch it with a labeled self-audit pass between draft and send: what was done vs. what was verified, each claim checked against the record.
rigor asymmetry: real rigor on work you review, less on work you're mid-production on

RULE 04Run the leave-one-out check even when the easy number is already wanted

The catch that matters most is the one nobody external asked for and that costs you a number you wanted. A file-disjoint split that isn't also individual- or site-disjoint can produce an excellent score that measures leakage rather than the thing you're modeling. Run the harder disjoint check anyway: the 0.9-to-0.103 collapse above is what it looks like when you do.
a good score on a non-disjoint split can be measuring the wrong construct entirely

RULE 05Corrections name the mechanism, and keep the old number visible

A correction states what was misread, what leaked, what field was mistaken for what. The mechanism is the content; regret is not. The old value is never quietly overwritten; it stays next to the new one, with the reason for the gap. Burying a correction under an apology is the same failure as never running the check: a confident conclusion stands unexamined until someone else pays for it.
apology without diagnosis erases the trail and makes the next error harder to catch

Two of these rules became live candidate detectors in this same pipeline, aimed at the exact patterns above: bare_done_claim (a completion word with no adjacent named verification, from Rule 01) and unqualified_metric_claim (a score reported with no n, split, or interval nearby, from Rule 02). The first is not hypothetical: bare_done_claim co-occurs with a tool error 627 times in this corpus, the single most common pairing in the whole dataset. The habit these rules describe and the failure the atlas catalogs are two views of one thing; the detectors are the bridge between them.

Run it on your own logs

Point the same pipeline at your own agent logs: plain Python, four commands, nothing to install, and your transcripts never leave your machine.

Everything above was computed by six plain-Python files in the open-science repo under docs/experiments/failure-atlas/pipeline/: extract.py, detectors.py, incidents.py, analyze.py, plus context_window.py for pulling transcript windows. Standard-library Python only, so if you have Python 3 you have the pipeline. Clone the repo, or read each file first on GitHub:

extract.py detectors.py incidents.py analyze.py context_window.py test_pipeline.py README.md pipeline/ on GitHub

Four commands, run from a working directory of your choice:

python3 pipeline/extract.py   --roots ~/.claude --db data/atlas.db
python3 pipeline/detectors.py --db data/atlas.db
python3 pipeline/incidents.py --db data/atlas.db --out data/incidents.jsonl
python3 pipeline/analyze.py   --db data/atlas.db --outdir data

What you get: atlas.db and incidents.jsonl stay on your machine, since they contain your text. analysis.json is the aggregates-only layer: totals and rates, no transcript content. That file is the one you could choose to share.

Or hand the job to your agent. Copy this prompt so your bot rebuilds the analysis from your own logs:

Fetch the pipeline files from the NimbleCoOrg/open-science repo, under docs/experiments/failure-atlas/pipeline/, into a local folder (clone the repo, or pull the raw files). Run, in order: extract.py --roots ~/.claude --db data/atlas.db, then detectors.py, incidents.py, and analyze.py against that same database. They are stdlib-only Python 3, so install nothing. When they finish, read data/analysis.json and report: my total sessions and events; my top five failure modes per 10k events; my incident-rate timeline by month; and where failures fall within my sessions. Then compare each against the reference numbers on this page (1,165 tool-error incidents at 16.4/10k; a timeline peaking at 86.3/10k; abandonment concentrated in the final tenth of sessions) and tell me where my logs differ most. Do not send, publish, or quote any transcript text; share data/analysis.json only.

The coding half of this is n=1, one operator and one workflow over seven months, but the assistant-fleet half is not. It is many different people across several agent harnesses and four chat platforms over the same span. Even so, it is one org's record. Medicine solved that problem without pooling patient records: hospitals share results computed by a common method over data that never moves (the OMOP model). analysis.json is that layer for agent logs. Forks running this same pipeline could pool their analysis.json files into a shared picture later, no transcripts moving. If a handful of people run these four commands and share only that file, "how do agents fail?" stops being one org's atlas and starts being a map. Share the results. Keep the data.

The feedback loop

Findings that don't change behavior are trivia. Each countermeasure names the metric that must drop.

The countermeasures follow one principle: no standing context. Nothing gets pasted into every session to be ignored by session forty. Instead:

  • Conditional hooks that fire only when their pattern is live. A completion-claim guard blocks "it's merged / it's running / verified" unless a verifying command actually ran, aimed at the 10-for-10 fault cluster. An error-streak nudge injects one line after four consecutive failures, aimed at the 491 error-loop incidents, where grinding continued past the point a human would have stepped back.
  • Atomic memory files: two of them, indexed, loaded only on demand, each holding one pattern the logs proved.
  • Settings recommendations, including quota-aware subagent spawning, aimed at the 26 subagent failures, every one of which ended its session.

Each augmentation ships with its falsification path: the metric that must drop, measured by re-running this same pipeline over post-install sessions. The baseline was snapshotted before anything was installed, so "it helped" gets measured against that snapshot rather than asserted. Nothing auto-installs; every hook is opt-in, and the next run of the pipeline is the judgment.
